# Quick-open 10k benchmark

Status: repeatable harness and recorded evidence. **Not** a CI threshold yet:
the numbers are evidence and an investigation tool, and no test fails because a
machine was busy.

This covers issue #42: certify key-to-results latency for the existing quick-open
palette on a deterministic 10,000-path workspace, then optimize only what the
measurement showed.

## What is measured

`rankFiles` / `rankIndex` — the synchronous work one keystroke performs:
normalise the query, score the already-loaded workspace path list, apply recent
file bonuses and keep the best rows.

| Included | Excluded |
| --- | --- |
| Query normalisation, scoring, recent-file bonuses, result cut | Filesystem access of any kind (the list is loaded once per workspace) |
| Ranking over 10,000 paths | DOM construction, layout and paint of the result rows |
| Cold first query and warm repeated queries | IPC, terminal, LSP and model/network latency |

Rows rendered and time-to-paint are deliberately out of scope: mixing them with
ranking would make the number depend on GPU, fonts and window size. The
distinction matters because the acceptance criteria forbid conflating LLM or
network time with palette latency; this harness never touches either.

## Fixture

`apps/desktop/ui/bench/quick_open_fixture.ts`:

- 10,000 **unique** relative paths, generated by a seeded Mulberry32 PRNG
  (`seed = 0x51A7`), so every machine and Node version sees byte-identical
  input. Nothing is read from disk.
- 16 top-level directories, 22 nested segment names, 33 realistic stems, file
  suffixes such as `-panel` / `-view` / `-test` and extensions `.ts`, `.tsx`,
  `.rs`, `.md`, `.json`, `.css` — depth up to five segments.
- Query shapes: empty (recents), one letter (near-total match), two letters,
  exact basename, common basename, fuzzy subsequence, fuzzy initials, path
  segments, camelCase basename, and a no-result query.

## Method

- **Cold**: a fresh copy of the path list, one `rankFiles` call. This is the
  first keystroke after the palette opens (index build included). 25 rounds.
- **Warm**: the same query repeated over the same list, 200 samples. Top-level
  awaits and the event loop are not involved, so this isolates ranking work.
- **Percentiles**: nearest-rank over the sorted samples, in milliseconds.
- The harness asserts invariants only (determinism, the 40-row cap, recents
  first, an empty result for a nonsense query). Timing is printed, never
  asserted.

```sh
cd apps/desktop
npm ci
npm run bench:quick-open
```

The harness lives in `ui/bench/quick_open_latency.bench.ts` and runs through
`vitest.bench.config.ts`, so `npm test` stays fast and no benchmark value can
become an accidental gate.

The table is one representative run from a quiet VM. Absolute values drift by up
to 2× between sessions on a shared host: the unfixed implementation measured
5.4 ms warm p50 for the empty query in the first session and 8.3 ms in a later
one on the same machine. Compare implementations inside one session (next
section), not two tables measured hours apart, and do not treat a single cell as
meaningful to two decimals.

Worst case across the suite in that run: **cold p95 9.055 → 4.394 ms**, **warm
p95 8.548 → 3.979 ms**. Across all repeated runs the worst observed values were
**cold p95 5.885 ms** (`e`) and **warm p95 4.624 ms** (`src/models`), both well
inside one 8 ms budget. The empty query and broad single-letter queries — the two
that match essentially all 10,000 paths — improved most (−61% to −68% warm p50).

### Interleaved comparison (reliable evidence)

Both implementations run alternately in one process, same 10,000-path fixture,
120 rounds per query, medians of the raw samples. The "old" column is the
shipped code, which rescans and re-lowercases the list, sorts every match and
uses `localeCompare` on every keystroke; the "new" column is what the palette now
does per keystroke — prepared index plus bounded top-K. Machine drift cannot
explain this table because both columns experience the same drift.

| Query | old p50 | new p50 | old p95 | new p95 | speed-up (p95) |
| --- | --- | --- | --- | --- | --- |
| empty (recents) | 8.274 | **0.452** | 11.573 | **0.647** | 18× |
| `e` (broad) | 11.229 | **2.113** | 16.926 | **2.662** | 6.4× |
| `ma` | 5.266 | **1.652** | 6.620 | **2.114** | 3.1× |
| `main` | 4.087 | **1.679** | 4.868 | **1.966** | 2.5× |
| `index` | 4.108 | **2.071** | 5.328 | **2.595** | 2.1× |
| `qopen` | 2.710 | **0.841** | 3.885 | **1.150** | 3.4× |
| `rct` | 8.076 | **2.669** | 11.879 | **3.105** | 3.8× |
| `src/models` | 4.379 | **2.347** | 6.054 | **2.964** | 2.0× |
| `quickOpen` | 3.758 | **1.157** | 4.417 | **1.265** | 3.5× |
| `zzznomatch` | 2.715 | **0.700** | 3.541 | **0.854** | 4.1× |

A second run of the same harness agreed within ~20%. The query-dependent spread
is expected: the win comes from removing per-path work (lowercasing, iterator
allocation) and per-match sorting, so queries that touch many paths gain most.

### Which change bought what

Both changes were driven by the measurement, and each was measured separately on
the same machine.

1. **Prepared index** (`buildQuickOpenIndex`, cached per loaded file list):
   lowercase paths and basenames once per workspace instead of 10,000
   `toLowerCase` calls per keystroke, plus one-time deduplication and a path set
   for recent-file filtering. Intermediate warm results: empty `5.419 → 4.834`
   p50 / `8.548 → 7.552` p95; `e` `5.657 → 5.158` / `7.141 → 7.647`; `rct`
   `4.760 → 3.879` / `6.611 → 5.366`.
2. **Bounded top-K + cheaper tie-break** (`insertBounded`, code-unit comparison
   instead of `localeCompare`): a broad query produced ~10,000 matches and then
   sorted all of them to show 40 rows. Keeping only the best 40 by
   binary-search insertion removed that sort, and replacing tens of thousands of
   `localeCompare` calls removed locale collation from the hot path. This is
   the step that took warm p95 from ~7.5 ms to ~3.0 ms for the broad queries.

The bounded path is required to return **exactly** the same order as
score-everything-then-sort: `quick_open_model.test.ts` compares the fast path
against a reference full-sort implementation for every benchmark query on the
10,000-path fixture, including truncated and custom-limit cases.

The only intended behavioural difference is the final tie-break among paths with
identical score *and* length: code-unit order instead of locale collation. It is
still deterministic, and it only affects visually indistinguishable candidates.

## Budget

Provisional, recorded so a future regression has a reference point:

| Measurement | Provisional budget | Observed worst |
| --- | --- | --- |
| warm p95 per keystroke (cached index) | ≤ 8 ms on this machine class | 3.11 ms |
| cold p95 (first query, index build included) | ≤ 12 ms | 5.89 ms quiet, 10.03 ms under CPU steal |

8 ms leaves half of a 60 Hz frame for result rendering. These are not enforced:
the benchmark is excluded from `npm test` and CI, per the issue's "benchmark is
not a CI pass/fail threshold until stable". A shared VM cannot even certify the
budget — the same cold query measured 5.9 ms and 10.0 ms on different runs while
the host was busy — so promoting this to a gate needs repeated runs on real
macOS/Windows/Linux developer hardware first.

Quick open must also never rescan the filesystem per keystroke: the palette ranks
the list already returned by `list_files`, and the index is rebuilt only when
that array identity changes.

## Limitations

- Ranking only. End-to-end "key pressed → pixels" latency needs a browser or
  WebView measurement and is not covered here.
- One shared Linux VM; no macOS or Windows numbers are recorded yet, and the
  numbers are V8/JIT specific.
- The fixture is synthetic. Real workspaces have similar path distributions but
  longer paths and more Unicode; the ranking code is ASCII-insensitive but the
  fixture does not stress non-ASCII collation.
- No 10,000-path test asserts a time limit. A regression is found by running the
  harness and comparing with the table above, not by CI.
